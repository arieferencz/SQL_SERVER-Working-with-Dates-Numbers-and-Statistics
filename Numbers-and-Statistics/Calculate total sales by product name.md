# Calculate total sales by product name

## 🎯 Exercise
Calculate the total sales amount for each product — showing the cumulative revenue generated by every product across all sales orders.

---

## 💡 Solution

### Approach
We join three tables to connect each sales order line to its product name. We then use `SUM()` on the `LineTotal` column grouped by product name to calculate the total revenue per product. `ROUND()` and `FORMAT()` are applied to present the amounts in a readable format.

### T-SQL functions and clauses used

| Function / Clause | Purpose |
|---|---|
| `INNER JOIN` (SalesOrderHeader → SalesOrderDetail) | Connects each order header to its individual order lines |
| `INNER JOIN` (SalesOrderDetail → Product) | Connects each order line to its product name |
| `SUM(LineTotal)` | Calculates the total sales amount per product across all orders |
| `ROUND(value, 2, 2)` | Rounds the result to 2 decimal places |
| `FORMAT(value, '#,#.##')` | Formats the result with comma thousands separators and 2 decimal places |
| `GROUP BY Product.[Name]` | Groups results by product name so `SUM()` produces one total per product |

### Tables used

| Schema | Table |
|---|---|
| `Sales` | `SalesOrderHeader` |
| `Sales` | `SalesOrderDetail` |
| `Production` | `Product` |

---

### T-SQL code

```sql
USE AdventureWorks2022;
GO

SELECT
    Product.[Name]
  , FORMAT(ROUND(SUM(SalesOrderDetail.[LineTotal]), 2, 2), '#,#.##') AS Total_Sales_By_Product_Name
FROM [AdventureWorks2022].[Sales].[SalesOrderHeader] AS SalesOrderHeader
INNER JOIN [AdventureWorks2022].[Sales].[SalesOrderDetail] AS SalesOrderDetail
    ON SalesOrderHeader.[SalesOrderID] = SalesOrderDetail.[SalesOrderID]
INNER JOIN [AdventureWorks2022].[Production].[Product] AS Product
    ON SalesOrderDetail.[ProductID] = Product.[ProductID]
GROUP BY Product.[Name]
```

## 🔍 Step-by-step explanation

### How the three tables connect

The three tables form a chain — each linked by a foreign key:

```
SalesOrderHeader          SalesOrderDetail              Product
─────────────────         ────────────────────          ──────────────
SalesOrderID ──────────► SalesOrderID                  ProductID ◄──── ProductID
                          ProductID ────────────────►
                          LineTotal
```

- `SalesOrderHeader` contains one row per sales order (31,465 orders total)
- `SalesOrderDetail` contains one row per order line — multiple lines per order (121,317 lines total)
- `Product` contains one row per product (266 products with sales)

`INNER JOIN` is used for both joins — only order lines that have both a valid order header and a valid product are included. Since `LineTotal` lives in `SalesOrderDetail`, this is the table whose column is summed.

### Query 1.2 — Apply `SUM()` and `GROUP BY`

`GROUP BY Product.[Name]` groups all 121,317 order lines by product name. `SUM(LineTotal)` totals all line amounts for each product — collapsing the 121,317 rows into 266 rows, one per product.

**Output (truncated):** 266 rows — one per product with its total revenue.

```

Full-Finger Gloves, L  155,321.46
...
(266 rows affected)
```

---

### Key observations from the output

- The query returns **266 rows** — one per unique product that appears in at least one sales order line
- Products are returned in alphabetical order by name (default behaviour of `GROUP BY`)
- `LineTotal` in `SalesOrderDetail` already accounts for quantity and unit price (`LineTotal = OrderQty × UnitPrice × (1 − UnitPriceDiscount)`) — so `SUM(LineTotal)` correctly reflects total revenue per product including discounts
- Some products like **Women's Mountain Shorts, S** (`$137,164.12`) and **Women's Mountain Shorts, L** (`$136,774.01`) generate more revenue than many better-known accessories despite lower unit sales volume — driven by a higher unit price

---

### Why `LineTotal` instead of `UnitPrice × OrderQty`?

`LineTotal` is the pre-calculated column in `SalesOrderDetail` that already applies the discount:

```
LineTotal = OrderQty × UnitPrice × (1 − UnitPriceDiscount)
```

Using `SUM(LineTotal)` is therefore more accurate than `SUM(UnitPrice × OrderQty)` — which would overstate revenue for discounted orders.
